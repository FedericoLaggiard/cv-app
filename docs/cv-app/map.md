# CV app — mappa Wayfinder

Label: `wayfinder:map`

## Destinazione

Una **spec scritta dell'MVP** di un'app Flutter per la gestione di CV, pronta da consegnare a chi implementa. La spec descrive: funzionalità, modello dati, formati file su disco, layer di persistenza per piattaforma, UX dell'editor, i template di export scelti e le librerie chiave. Nessuna riga di codice di produzione: solo prototipi cheap dove servono per decidere.

## Notes

**Dominio**: gestione curriculum — creare, mantenere aggiornati, avere più *varianti* (una per tipologia di candidatura), importare CV esistenti in PDF, esportare in PDF con template diversi.

**Vincoli fissi (già decisi, non discutere di nuovo)**:
- Flutter, unica codebase per mobile + desktop + web
- Nessun backend, solo front-end
- Persistenza: file system reale su desktop/mobile, IndexedDB/LocalStorage su web con import/export manuale dei file
- Versioning = **varianti nominate** (file separati indipendenti); niente cronologia stile git nell'MVP
- Modello dati = **schema fisso ricco + sezioni custom aggiuntive**
- Export MVP: **solo PDF**
- Template: **hard-coded come Flutter widget in Dart** (niente template engine dichiarativo per l'MVP)
- 2–3 template nell'MVP
- LLM assistant (versione job-tailored del CV) = **fuori scope MVP** (v2)
- State management = **Bloc + Cubit** (`flutter_bloc`); nessun'altra libreria di state management da valutare nel ticket 06
- **Import PDF = auto-import puro** nell'MVP; import assistito → v2
- **OCR** per PDF scansionati → **v2**
- **Licenze**: solo librerie con licenza open source / permissiva; escluse Syncfusion Community, Apryse e simili a prescindere dal merito tecnico

**Skill utili nelle sessioni successive**:
- `/grilling` e `/domain-modeling` per i ticket di tipo grilling (default)
- `/prototype` per i ticket di prototipo (UX editor, template)
- `/research` per i ticket di ricerca (import PDF, scelta stack)

**Lingua**: la conversazione è in italiano; gli artefatti (spec, ticket) sono in italiano.

## Decisioni finora

<!-- Un rigo per ticket chiuso: gist della risposta + link. -->

- [Schema dati del CV (sezioni fisse e campi tipizzati)](issues/01-schema-dati-cv.md) — 8 sezioni fisse (Anagrafica, Contatti, Sommario, Esperienze, Formazione, Skill, Lingue, Certificazioni), Anagrafica/Contatti separate e indipendenti, campi tipizzati con obbligatori minimi (nome/cognome, email/tel opzionali, ruolo+azienda+data inizio per Esperienze, titolo per Formazione, lingua+livello CEFR per Lingue, nome+ente per Certificazioni), **rich text = Markdown** trasversale a tutti i campi lunghi, Skill = Markdown + lista di tag liberi, date = mese+anno, ordine di default fissato.
- [Sezioni custom aggiuntive](issues/02-sezioni-custom.md) — Sezione custom = **titolo + blob Markdown**, per-variante, nessun limite di numero. **Ordine globale libero** su tutte le sezioni (fisse + custom): il CV serializza una lista ordinata. Identità sezione = **`kind` immutabile** (enum chiuso per le fisse, `"custom"` per le custom) + **`displayTitle` modificabile** dall'utente. Sezioni fisse rinominabili e **rimovibili** senza limiti per variante. Vincolo unicità: i `displayTitle` presenti in una variante devono essere univoci. Rendering: ogni template ha un renderer per `kind` strutturato + un unico **block-renderer Markdown** riusato per `summary` e per tutte le custom.
- [Formato di serializzazione dei file CV](issues/03-formato-file-cv.md) — **JSON minified UTF-8**, un file per variante, estensione **`.cvapp`**, asset binari (foto) **embed in base64** in un `assets` store indirizzato per `assetId`. Root con `id: UUID v4` + `createdAt`/`updatedAt` + `variantName` + `schemaVersion: intero` (parte da 1, catena di migrazioni **forward-only in-app**, refuse-if-newer, **strict su campi sconosciuti**). Sezioni = lista ordinata `sections[]` di `{kind, displayTitle, data, [id]}`; sezioni fisse identificate dal `kind` (unicità per variante), custom con `id: UUID` immutabile, item delle sezioni-lista (esperienze/formazione/lingue/certificazioni) ognuno con `id: UUID`. Date `"YYYY-MM"` + flag `current` per "in corso", enum sempre stringhe canoniche snake_case ASCII. GC al save degli asset non più referenziati. Portabilità: `.cvapp` autocontenuto e rinominabile senza perdere identità logica.
- [Layer di storage per piattaforma](issues/04-storage-per-piattaforma.md) — **Library-based** su tutte le piattaforme (nessun modello document-based): l'app gestisce una libreria locale in cartella **app-managed nascosta** (`path_provider` su desktop/mobile, IndexedDB su web). File nella libreria nominati `<uuid>.cvapp`; l'export usa `<variantName sanitizzato>.cvapp`. Su web: un solo object store `variants`, key = UUID, value = oggetto JSON completo con asset base64, index `by_updatedAt`. **Auto-save** con debounce ~800ms, **write atomico via tmp+rename** su desktop/mobile. **Nessun controllo di concorrenza** (last-write-wins). File corrotto → badge "⚠ corrotta" + azioni esporta-grezzo/elimina; **niente backup automatico** nell'MVP. Interfaccia astratta **`CvRepository`** ibrida: `Stream<>` per viste (`watchAll`, `watch`) + `Future<>` per azioni (`create`, `duplicate`, `save`, `delete`, `importFromBytes`, `exportToBytes`); `Uint8List` come solo contratto verso il mondo esterno; `ImportResult` sealed (success/conflict/corrupt). Doppio-click / share-in di un `.cvapp` esterno → **auto-import silenzioso** + toast con "Annulla".
- [Ricerca fattibilità import PDF](issues/05-ricerca-import-pdf.md) — Candidate primarie: **`pdfrx`** (MIT, tutte le piattaforme incluso Web WASM, testo+bounding box, no font/stile) e **`syncfusion_flutter_pdf`** (community license, estrazione ricca con font/stile, no-FFI). **Auto-mapping completo eliminato**: template creativi/multi-colonna hanno ordine di lettura instabile e attribuzione a sezioni fragile → strategia MVP = **import assistito** (estrai testo con bbox → UI affiancata → utente riversa nei campi). `pdf_text` morto; `pdfx`/`native_pdf_*`/`printing` sono viewer, non parser; PDFium via FFI non gira su Web. **OCR** per scansionati: `flutter_tesseract_ocr` ok su mobile+web, desktop richiede packaging nativo → decisione perimetro deferita. Raccomandazione analista: `pdfrx` primario, `syncfusion` piano B se licenza accettata. Report: [assets/05-ricerca-import-pdf-report.md](issues/assets/05-ricerca-import-pdf-report.md).
- [Scelta della libreria PDF per l'import](issues/10-scelta-libreria-pdf.md) — **Strategia di import MVP = auto-import puro**: l'app estrae dal PDF e apre l'editor pre-riempito con quello che è riuscita a mappare; frammenti non mappati scartati; editor normale come superficie di correzione; **nessuna UX di revisione dedicata** (import assistito → v2). **Libreria primaria: `pdfrx`** (MIT, cross-platform reale incluso Web WASM, estrazione strutturata con `charRects`). Syncfusion escluso per policy: nessuna libreria con licenza non-open. Alternative FFI a PDFium scartate perché no-Web. **Cosa perdiamo**: font metadata espliciti → sostituiti da **proxy geometrici** (altezza bbox ∝ font size, spaziatura verticale per gerarchia titoli) nelle euristiche di ticket 13. **Piano B = graceful degradation** (nessuna libreria di riserva): password → prompt; scansionato → messaggio esplicito (OCR = ticket 12); layout caotico → mappa il possibile, resto vuoto; bug Web WASM → disabilitare import su Web. Ticket 11 chiuso come fuori scope MVP; 12 e 13 sbloccati.
- [Strategia OCR per PDF scansionati](issues/12-strategia-ocr-scansionati.md) — **OCR fuori scope MVP → v2**: caso d'uso statisticamente marginale (i CV nascono digitali), costo cross-platform sproporzionato (`flutter_tesseract_ocr` non copre desktop out-of-the-box), bundle gonfiato dai language pack (~30-50 MB per ita+eng), qualità comunque incerta su layout creativi. **Rilevamento scansionato**: `avgCharsPerPage < 100` dopo `pdfrx.loadStructuredText()` (soglia relativa, robusta a briciole di OCR residuo, tollera CV cortissimi). **UX degradata**: dialog con testo *"Il PDF sembra un'immagine scansionata..."* + due azioni *Crea CV da zero* / *Annulla*. Nessuna opzione "importa quel poco che c'è" — le briciole di testo residuo sarebbero rumore, contro la strategia conservativa del ticket 10.
- [Euristiche di mapping testo estratto → schema CV](issues/13-euristiche-mapping-pdf.md) — Filosofia **conservativa** (precisione > recall, no confidence UI). Pipeline ibrida: (1) **signal-first globale** con regex → Contatti (email, telefono, LinkedIn/GitHub/URL generico → lista `Link[]`); (2) **section-first** con dizionario italiano+inglese + isolamento sulla riga + proxy geometrico (altezza bbox); fallback anti-disastro: se < 2 titoli riconosciuti, section-first disabilitato. (3) Testo non attribuito → sezione custom **"Da rivedere"**. **Non auto-riempiamo**: nome/cognome, headline, foto (→ ticket 09), ruolo/azienda dentro Esperienze, titolo/ente dentro Formazione. Item grouping in Esperienze/Formazione: split per data → fallback riga vuota → fallback intero blocco come custom section. Campi item: date estratte + `descrizione` = intero raw dell'item; ruolo/azienda/titolo/ente lasciati vuoti (l'utente ritaglia dalla descrizione nell'editor). Sezioni non strutturabili (Sommario/Skill/Lingue/Certificazioni) se riconosciute → sezioni custom col titolo originale, mai riempimento dei campi strutturati. Date: mese+anno IT+EN esteso/abbreviato, numerici, range con trattino/en-dash/em-dash, marker "in corso"; solo-anno accettato solo dentro range o accanto a mese, normalizzate a `YYYY-MM`.
- [Scelta dello stack Flutter](issues/06-scelta-stack-flutter.md) — Stack MVP definitivo: **routing** `go_router` (BSD-3-Clause), **PDF export** `pdf` + `printing` (Apache-2.0, DavBfr), **file picker** `file_picker` v12 (MIT, incluso `saveFile()`), **save/share** `share_plus` (mobile+Web) + `file_picker.saveFile()` (desktop+lacuna Linux), **storage web** `idb_shim` (BSD-3-Clause, thin wrapper IndexedDB WASM-compatible), **JSON** `freezed` **v3.x pinned** (v4 troppo fresca) + `json_serializable`, **Markdown rendering** `flutter_markdown_plus` (⚠️ `flutter_markdown` discontinued), **Markdown editor** `super_editor` via GitHub + `super_editor_markdown` (approccio WYSIWYG con storage Markdown puro; fallback documentato = TextField + toolbar custom se `super_editor` risulta instabile). **Esclusi per licenza**: `appflowy_editor` (AGPL-3.0), Syncfusion, Apryse. Report: [assets/06-stack-flutter-report.md](issues/assets/06-stack-flutter-report.md).
- [Gestione foto profilo e asset](issues/09-gestione-foto-e-asset.md) — **Un solo asset supportato nell'MVP**: foto profilo referenziata da `Anagrafica.fotoProfiloAssetId`, opzionale. No immagini in Markdown, no libreria media. **Formati accettati**: jpg/jpeg/png/webp; **rifiutati**: HEIC (decoder cross-platform problematico), GIF/SVG/BMP/TIFF. **Nessun crop obbligatorio all'upload** — il clip lo decide il template PDF. **Normalizzazione all'ingest**: resize max 800×800 (aspect ratio preservato, no upscaling) + JPEG Q=85; hard cap **500 KB** post-normalizzazione con retry a Q decrescente (75/65) prima di fallire. **Storage**: base64 dentro `assets` store del JSON come `{mimeType: "image/jpeg", data: "<base64>"}` (coerente col ticket 03). **Template PDF** ricevono `Uint8List` JPEG via `pw.MemoryImage`; ogni template gestisce sia foto-presente sia foto-assente (layout adattato). Portabilità automatica via `.cvapp` autocontenuto.
- [UX dell'editor del CV](issues/07-ux-editor.md) — Layout largo (desktop nativo + web desktop paritari) = **due colonne**: sidebar-indice cliccabile (jump-to, con badge ⚠ per obbligatori mancanti) + editor a **scroll unico**. **Sezioni collassabili** come blocco intero via chevron nell'header (click su header o chevron); default espanse; `Comprimi tutte` / `Espandi tutte` nella sidebar/bottom-sheet; jump-to dall'indice espande automaticamente; stato di collapse **non serializzato** in `.cvapp`. Voci sezioni-lista **sempre espanse**, nessun collapse per voce. Rich text via `super_editor` WYSIWYG con **toolbar sempre visibile** in cima al campo attivo (sopra la tastiera su mobile). Riordino sezioni + voci = **drag handle** primario (solo l'handle avvia il drag) + **menu contestuale** ("Sposta su/giù/in cima/in fondo") come fallback accessibile. Aggiunta esposta in doppio punto: `+ Aggiungi sezione` in fondo allo scroll **e** nella sidebar; `+ Aggiungi voce` in header sezione **e** in coda. Dialog unico `Aggiungi sezione` mostra sezioni fisse rimosse (radio) + "Sezione personalizzata". Validazione obbligatori = **marker soft** (badge ⚠ indice/header sezione/header voce, visibile anche su sezione collassata), nessun blocco durante l'editing, riepilogo bloccante-soft all'export con "Esporta comunque". **Live preview PDF = route/schermata a pagina piena** su entrambi i form factor, con thumbnail template in cima e rigenerazione manuale (banner "Anteprima non aggiornata"); cambio template non tocca i dati. Auto-save 800ms + indicatore in top bar (`Salvato ✓` / `Salvataggio…` / `⚠ Errore [Riprova]`). **Mobile** = colonna singola, indice come **bottom sheet**. **Avvio app** = schermata **Libreria** con card variante + card `Nuova` (menu Da zero / Da PDF / Duplica); stato vuoto con CTA verticali. Tablet non è categoria separata: layout largo per finestra ≥ 900px, mobile sotto. Wireframe completi: [assets/07-ux-editor-wireframes.md](issues/assets/07-ux-editor-wireframes.md).
- [Design dei 2–3 template di export PDF](issues/08-design-template.md) — **3 template hard-coded**: **Classico** (singola colonna, EB Garamond, solo neri/grigi, ATS-friendly, foto opzionale in alto-dx 28×36mm), **Moderno** (due colonne asimmetriche, banda `#1f2d3d` a sinistra ~29% con foto Ø40mm + contatti + skill + lingue, colonna principale bianca con accent `#2b6cb0`, Inter, **banda solo sulla prima pagina** poi colonna piena larghezza), **Minimal** (singola colonna stretta ~72 caratteri, Inter uppercase per label + EB Garamond serif per body, zero colori, **ignora la foto per design**). Font open-source SIL OFL embed (EB Garamond + Inter + JetBrains Mono, ~1.2MB Latin Extended). **A4 hard-coded**, Letter → v2 (nessun campo `pageFormat` nel `.cvapp` ora). Ordine sezioni = quello serializzato in `sections[]`, template non riordinano. Block-renderer Markdown unico (bold/italic/liste/link) riusato per Sommario + sezioni custom. `pw.MultiPage` con `keepTogether` su header sezione + primo item. Wireframe: [assets/08-design-template-wireframes.md](issues/assets/08-design-template-wireframes.md).
- [Sub-flow di gestione delle varianti (rinomina, duplica, elimina)](issues/14-sub-flow-gestione-varianti.md) — **Univocità `variantName` hard case-insensitive + trim** su tutta la libreria; validazione live inline in tutti i dialog che assegnano un nome. **Rinomina** = dialog modale singolo campo, il file `<uuid>.cvapp` non cambia nome (identità = UUID interno), auto-save 800ms. **Duplica** da card variante: dialog con default `<origName> (2)` incrementale al primo slot libero (pattern `^<name> \((\d+)\)$` case-insensitive); da card `Nuova`: dropdown sorgente (ordinata per `updatedAt` desc) + campo nome che si auto-aggiorna al cambio sorgente; nuovo UUID + `createdAt = updatedAt = now()`, copia per valore, nessuna relazione originale-copia persistita. **Elimina** = dialog conferma semplice (`[Annulla] [Elimina]` destructive), **hard-delete immediato senza undo, senza cestino, senza toast Annulla** (coerente con "no backup automatico" del ticket 04); se la variante era aperta l'app torna a Libreria. **Cross-piattaforma**: menu `[⋯]` sulla card apre **popup menu** su desktop/web-desktop (≥ 900px) e **bottom sheet** su mobile (< 900px); dialog rinomina/duplica/conferma-elimina restano modali su entrambi i form factor; solo `[⋯]` come porta d'accesso, no long-press. **Amendment ticket 04**: `.cvapp` esterno con nome in collisione → **auto-rinomina silenziosa** con suffisso `(N)` + toast informativo standard; `ImportResult.conflict` resta per collisione di UUID.
- [Internazionalizzazione (app e CV)](issues/15-internazionalizzazione.md) — **UI dell'app in italiano + inglese** da subito via `flutter_localizations` + ARB (`app_it.arb`, `app_en.arb`); default segue il sistema, **fallback su inglese**. Nuova schermata **Impostazioni** (icona ingranaggio in top bar Libreria) con lista estendibile: nell'MVP contiene solo `Lingua interfaccia` (radio Sistema/IT/EN); preferenza persistita via `shared_preferences` (chiave `ui_locale`), fuori da `.cvapp` e fuori dalla libreria (è per-installazione). **CV multilingua = via varianti nominate**, nessun campo `language` nello schema, nessun campo multilingua per valori (schema del ticket 01 invariato). **Template PDF localizzati IT+EN** con tabella `Map<LabelLocale, Labels>` e rendering date via `intl.DateFormat`; scelta della lingua **esplicita nel dialog di export** (dropdown `Lingua etichette`, default = lingua UI corrente), scelta indipendente per ogni export. **Live preview** include lo stesso dropdown e usa la scelta come default per il dialog di export. **`.cvapp` invariato**: date `YYYY-MM` locale-neutre, enum snake_case ASCII. **Amendment ticket 06**: aggiunta `flutter_localizations` + `intl` (SDK/companion) + `shared_preferences` (BSD-3-Clause). **Amendment ticket 07**: nuova schermata Impostazioni + dropdown `Lingua etichette` in live preview. **Amendment ticket 08**: label template diventano tabella `Map<LabelLocale, Labels>`, funzione render prende `LabelLocale`.
- [Testing E2E dell'app Flutter pilotato da agente AI](issues/17-e2e-testing-flutter.md) — Vincolo solo-dev su macOS senza CI multi-host: **E2E automatizzato locale su iOS Simulator + Android Emulator + Chrome + macOS Desktop**; Windows/Linux Desktop = build + smoke manuale. Flow obbligatori sul set eseguibile: create-variant, edit strutturato, rename/duplica/elimina, export PDF (magic bytes), auto-save. Import PDF su Web segue "test = verità di produzione" del ticket 10 (Esito A: E2E su Chrome; Esito B: verifica che sia disabilitato). **Desktop dialogs**: fake `FileSystemService` via DI dietro `--dart-define=E2E=true`, no AppleScript. **Web**: renderer default + `SemanticsBinding.ensureSemantics()` in test build; **solo Chrome** in E2E, Firefox/Safari = smoke manuale. **Esecuzione 100% locale via Makefile** (`make e2e-ios/android/web/macos/all`), nessuna CI oggi. **`super_editor`**: backdoor `TestHooks.setEditorContent(key, markdown)` per popolare rapidamente + 1 solo E2E "editor felice" + formattazione fine coperta da widget test (no E2E). Amendment ticket 06 (`patrol` + `patrol_cli` dev-dep), 07 (appendix `Key` semantiche stabili + hook rich text), 04/06 (contratto `FileSystemService`). **Contratto MCP agente-driven (area 5) fuori scope MVP → v2**, materiale esplorativo conservato nel ticket.
- [Onboarding del primo utente](issues/16-onboarding-primo-utente.md) — **Tour guidato skippabile a 5 card** al primo avvio, presentato come **overlay a schermo intero** sopra la Libreria (backdrop `Colors.black54`, card centrata; frecce laterali `◀`/`▶` + `Salta`/`Avanti`/`Inizia` su desktop, swipe orizzontale su mobile). ## Fuori scope

<!-- Lavoro deliberatamente escluso dalla destinazione. Non graduerà mai in ticket. -->

- **LLM assistant** per generare varianti tailored su una job description → v2, richiesto esplicitamente come futuro. Include anche la **traduzione automatica dei CV via LLM** (dalla lingua sorgente della variante a una lingua target, generando una nuova variante) — stessa area, stesso scope v2.
- **Formato pagina Letter** (215.9×279.4 mm, standard nordamericano USA/CA) → v2. L'MVP hard-coda A4; il `.cvapp` non serializza `pageFormat` ora, si aggiungerà via schema migration quando arriverà Letter. Vedi [Design dei template](issues/08-design-template.md).
- **Sincronizzazione automatica tra dispositivi** (stesso utente su PC + telefono + web che vede la stessa libreria) → v2, da approfondire. L'MVP è library-based con librerie locali indipendenti per installazione; il trasferimento cross-device passa per export/import manuale del `.cvapp`. Post-MVP valutare: cartella cloud user-managed (iCloud/Drive/Dropbox) come location della libreria, oppure backend leggero dedicato — con relative implicazioni su edit concorrenti e conflitti.
- **Formati di export oltre il PDF** (DOCX, HTML, JSON export) → l'MVP fa solo PDF.
- **Cronologia stile git** (snapshot storici di un singolo CV) → si usa il modello a varianti nominate.
- **Sync cloud / backend / account utente** → l'app è dichiaratamente front-end only.
- **Template estendibili dall'utente / marketplace di template** → i template sono hard-coded nell'MVP.
- **Automazione E2E agente-driven via MCP** (skill che, a implementazione conclusa, genera il file di test dalla sezione `## Accettazione E2E` del ticket, lo esegue su tutte le piattaforme target via `patrol_mcp`, e itera in loop di riparazione fino al verde) → **v2**. Nell'MVP i test E2E si scrivono a mano seguendo la struttura Patrol standard. Materiale esplorativo (server MCP candidato, formato del contratto di accettazione, tool custom `list_keys`/`list_test_hooks`, skill `/implement-cv`, prerequisiti d'ambiente) conservato nella sezione finale del [ticket 17](issues/17-e2e-testing-flutter.md) come input per la sessione futura. Motivo del rimando: senza un corpus di ticket già implementati non si può tarare il formato del contratto, e introdurre il flusso ora creerebbe più problemi che benefici.
